2. `spec/campaigns.test.ts` strengthens the existing same-tile construction race:
   both server admissions must occur within the same timestamp second, one
   placement succeeds and the other conflicts, and both users agree on the result.
   Its existing seat race and ownership checks remain.
3. `spec/multiplayer-crash.test.ts` uses a child process and SIGKILL after an
   acknowledged core placement has reached the peer stream. It does not call
   graceful application shutdown before the kill. After restarting against the
   same temporary save, the owner reopens the room, the account peer re-enters,
   both retain their pilot IDs and see the same single core and a working stream.
   This tests application process failure, not host power loss or disk durability.

All automated fixtures use temporary saves. They do not modify the supplied
Fly campaign, live machine count or production volume.

### G: separate-machine test and current limitation

The application currently uses process-local room/visit registries and live
streams (`campaigns/service.js`) plus SQLite files in the mounted data directory
(`server.js`). `fly.toml` describes the course's one-machine/one-volume baseline.
There is no shared room coordination or cross-machine state replication in this
implementation. A local two-room test verifies isolation, not distributed sharing.

Fly volumes are attached to individual Machines and their contents are not
automatically replicated. Scaling therefore does not make the current shared
world distributed. [Fly volume documentation](https://docs.fly.io/volumes/overview)

Prepare a disposable deployment with a deliberate state-sharing/room-routing
strategy before treating this as an expected passing test. Merely copying the
SQLite file once does not synchronize subsequent changes or in-memory rooms.
On that disposable deployment, the requested command is:

```sh
mise exec -- flyctl scale count 2 -a <disposable-test-app>
mise exec -- flyctl machine list -a <disposable-test-app>
```

`scale count` changes the number of Machines; it does not guarantee that two
browser sessions are routed to different Machines. Record serving instance IDs
for each tested request/stream using deployment diagnostics, then run B/C/D/E.
If both clients land on one Machine, G is inconclusive. If one cannot find the
room/session or each machine accepts a different winner, record the failure.
[Fly scale-count reference](https://docs.fly.io/flyctl/cmd/fly_scale_count)

No production scale change was performed for this report. A passing version of
G requires architecture work beyond adding tests.

for this actual Fly run. Never reset the campaign or replace its volume to make
